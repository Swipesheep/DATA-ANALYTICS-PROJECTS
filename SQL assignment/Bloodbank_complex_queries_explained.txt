-- Q15. Stored Procedure — RegisterDonation
-- WHY COMPLEX:
--   • Not just a query — it's a full program inside the DB
--   • Uses IN/OUT parameters (inputs + an output message)
--   • Has DECLARE variables to store temporary values
--   • Contains IF/ELSE logic to decide eligibility
--   • Runs 3 INSERT statements in sequence:
--       Step 1 → Insert health screening record
--       Step 2 → Insert donation record (only if eligible)
--       Step 3 → Insert into blood inventory (only if eligible)
--   • Uses LAST_INSERT_ID() to chain the three inserts together
--   • Uses a CASE expression to calculate expiry date
--     based on donation type (Whole Blood=42d, Plasma=365d, etc.)
--   • Uses DELIMITER $$ to allow semicolons inside the procedure
-- WHAT IT DOES IN SIMPLE TERMS:
--   You call this procedure once with donor health data.
--   It automatically decides if the donor is eligible,
--   records the screening, records the donation, and
--   adds the blood unit to inventory — all in one step.
-- ─────────────────────────────────────────────────────────

-- Q17. VIEW — vw_DonorEligibility
-- WHY COMPLEX:
--   • Uses a correlated subquery inside a CASE expression —
--     a query inside a query inside a condition
--   • The subquery runs separately for EACH donor row
--     to find their most recent screening result:
--       (SELECT is_eligible FROM DonorHealthScreening
--        WHERE donor_id = d.donor_id
--        ORDER BY screening_date DESC LIMIT 1)
--   • The CASE has 3 conditions checked in order:
--       1. Is the donor marked inactive?
--       2. Did they fail their last health screening?
--       3. Has it been less than 56 days since last donation?
--       4. Otherwise → Eligible
--   • Uses LEFT JOIN so donors with zero donations still appear
--   • Uses GROUP BY with MAX() to find the most recent donation
--   • Uses DATEDIFF() to calculate days since last donation
-- WHAT IT DOES IN SIMPLE TERMS:
--   Creates a reusable summary table showing each donor's
--   current eligibility status and when they last donated.
--   You can just query: SELECT * FROM vw_DonorEligibility
-- ─────────────────────────────────────────────────────────

-- Q2. Total Stock vs Pending Requests (Supply vs Demand)
-- WHY COMPLEX:
--   • Uses CTEs (WITH clause) — two named temporary tables:
--       Supply CTE → calculates available blood per group
--       Demand CTE → calculates pending request units per group
--   • Uses FULL OUTER JOIN — keeps rows from BOTH sides
--     even if one side has no match (e.g., a blood group
--     has supply but no demand, or demand but no supply)
--   • Uses COALESCE() to replace NULL with 0 so math works
--     (NULL - 5 would break without COALESCE)
--   • Calculates net_balance = supply minus demand
--   • Uses a CASE to label each blood group:
--       SHORTAGE / OUT OF STOCK / Sufficient
-- WHAT IT DOES IN SIMPLE TERMS:
--   Compares how much blood is available vs how much
--   has been requested but not yet fulfilled.
--   Flags which blood groups are running short.
-- ─────────────────────────────────────────────────────────


-- ─────────────────────────────────────────────────────────
-- Q11. Blood Group Compatibility Check
-- WHY COMPLEX:
--   • Uses a subquery inside the WHERE clause
--   • The subquery uses a VALUES() table constructor —
--     an inline mini-table listing compatible blood groups:
--       SELECT compatible_group FROM (
--           VALUES ('B+'), ('B-'), ('O+'), ('O-')
--       ) AS compat(compatible_group)
--   • The outer query then filters inventory to only show
--     units from blood groups in that inline table
--   • Blood compatibility rules are hardcoded inline
--     (B+ recipient can receive from B+, B-, O+, O-)
-- WHAT IT DOES IN SIMPLE TERMS:
--   Given a recipient's blood type (e.g., B+),
--   find all available inventory units that are
--   compatible and safe to transfuse to them.
-- ─────────────────────────────────────────────────────────

-- WHY COMPLEX:
--   • Uses string concatenation (|| operator) inside CASE
--     to build a single "detected_diseases" column by
--     combining up to 5 disease flags into one string:
--       CASE WHEN has_hiv THEN 'HIV ' ELSE '' END ||
--       CASE WHEN has_hepatitis_b THEN 'Hepatitis-B ' ELSE '' END || ...
--   • Each CASE produces a piece of text or empty string,
--     and || joins them all together
--   • Filters using multiple OR conditions in the WHERE clause
-- WHAT IT DOES IN SIMPLE TERMS:
--   Shows donors who tested positive for any disease,
--   and lists all their diseases in one readable column
--   like: "HIV Hepatitis-B"

-- Q16. VIEW — vw_BloodAvailability (Dashboard)
-- WHY COMPLEX:
--   • Uses a conditional SUM with CASE inside it:
--       SUM(CASE WHEN DATEDIFF(expiry_date, CURDATE()) <= 7

--     This counts only bags expiring within 7 days
--     by treating each qualifying row as 1 and others as 0
--   • Filters to only show non-expired, non-contaminated,
--     available units simultaneously
--   • Creates a VIEW so this is always live/up-to-date
-- WHAT IT DOES IN SIMPLE TERMS:
--   A live dashboard view showing available blood by group
--   and type, including a warning count for bags expiring
--   within the next 7 days.
-- ─────────────────────────────────────────────────────────
